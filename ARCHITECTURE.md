# webOS Foundry — architecture contract

This file is the frozen interface every module, script and integration builds against. It exists
so the CLI, the HTTP server, the TV-side scripts and the Home Assistant integration can be built
and tested independently and still fit together on the first try. Changing a signature here means
updating every caller listed under "Consumers".

Prerequisite: the TV is already rooted (Homebrew Channel / webosbrew, e.g. via the separate
`slopbro` exploit or any other rooting method) and reachable over SSH as `root` with some existing
key or password. webOS Foundry never roots a TV and never asks for the LG account.

## 1. Repository layout

```
webos_foundry/          Python package (the "core"), importable, zero required dependencies
  config.py              on-disk config: load/save, defaults, paths
  transport.py           Transport protocol + SSHTransport (talks to the TV)
  dispatcher.py          builds the exact SSH_ORIGINAL_COMMAND strings the TV-side dispatcher accepts
  tv.py                  status, remote, settings (uses transport + dispatcher)
  notify.py              toast / say / overlay
  capture.py             screenshot (luna) + live stream (native vtcap)
  process.py             image / audio AI-pipeline processing (profiles, validation)
  pairing.py             wof pair: bootstrap dispatcher + dedicated key using the user's root key
  install.py             wof install/update/uninstall: push/refresh TV-side assets over the dedicated key
  server.py              HTTP API + static web UI host, with bearer-token auth
  cli.py                 argparse CLI ("wof"), one subcommand per capability
  errors.py              shared exception types
tv-assets/               files pushed to the TV; path below is also used as the "name" in INSTALL_FILES
  dispatch.sh             forced-command entry point (see §3)
  status.sh               status reader (power/foreground/temperature)
  details.js               read-only sensors (lux, panel, usage, signal, sleep timer)
  notify.js                toast / say / overlay card launcher
  settings.js               AI picture/sound settings read + write
  remote.js                remote keys, HDMI switch, volume/mute, power off
  process-image.js          image AI-pipeline processor (runs under the TV lock)
  process-audio.js          audio AI-pipeline processor (runs under the TV lock)
  overlay/                  the on-screen overlay web app (appinfo.json, index.html, overlay.js, overlay.css, icon.png)
  vtcap/                    native fast-capture client (vtcap.c, build.sh); vtcap binary is built, not committed
web/                      static web UI served by `wof serve` (index.html, app.css, app.js)
homeassistant/custom_components/webos_foundry/   HA custom integration (talks to the HTTP API only)
docs/                     user-facing documentation
scripts/                  maintenance scripts (gen_api_docs.py, etc.)
tests/                    pytest, offline only — every test uses a FakeTransport, never a real TV
```

## 2. Config

`webos_foundry.config.Config`, persisted as JSON at `$WEBOS_FOUNDRY_HOME` (default
`~/.config/webos-foundry`), file `config.json`, mode 0600:

```json
{
  "tv_host": "192.168.1.50",
  "ssh_port": 22,
  "key_path": "<config dir>/id_ed25519",
  "known_hosts_path": "<config dir>/known_hosts",
  "mac": "AA:BB:CC:DD:EE:FF",
  "broadcast": "192.168.1.255:9",
  "server_token": "<random 32-byte urlsafe token, generated by `wof pair` or `wof serve --generate-token`>"
}
```

`key_path`/`known_hosts_path` point at files `wof pair` creates; they are never the user's own root
key. `mac`/`broadcast` are used only for Wake-on-LAN and are optional (status/remote/etc. work
without them; `wof remote wake` fails with a clear message if `mac` is unset).
`Config.load()`/`Config.save()` raise `webos_foundry.errors.ConfigError` on a missing or malformed
file; every command that needs a paired TV calls `Config.require()`, which raises
`NotPairedError` pointing at `wof pair --host <ip>`.

**Consumers:** every module below; `cli.py` wires `--config-dir` to override `WEBOS_FOUNDRY_HOME`.

## 3. Transport and the TV-side dispatcher

```python
class Transport(Protocol):
    def run(self, command: str, data: bytes = b"", timeout: float = 20) -> bytes: ...
    def run_streaming(self, command: str, timeout: float = 20) -> subprocess.Popen: ...  # stdout is a pipe; used only by capture.stream()
```

`run` raises `webos_foundry.errors.TransportError(message)` on a non-zero exit or a connection
failure; `message` is the TV's stderr when available. `SSHTransport(config)` shells out to the
system `ssh` binary (`IdentitiesOnly=yes`, `BatchMode=yes`, `StrictHostKeyChecking=yes`,
`UserKnownHostsFile=<config known_hosts>`, `WarnWeakCrypto=no`, `ClearAllForwardings=yes`,
`ConnectTimeout=5`) using `config.key_path`; `command` is sent as `SSH_ORIGINAL_COMMAND` (the SSH
server's forced-command feature ignores the command baked into `command=` in `authorized_keys` and
exposes the client's request string through that environment variable instead — this is exactly how
the dedicated key stays restricted). Tests substitute `FakeTransport`, a recorder with a scripted
`run`/`run_streaming` map; no module in `webos_foundry/` ever imports `subprocess` directly outside
`transport.py` and `pairing.py` (which also needs a one-off transport using the user's *own* root
key — see §6).

### Dispatcher grammar (`tv-assets/dispatch.sh`)

One forced command, one regex per verb, never `eval`. Every argument after the verb is validated
server-side again (base64 charset, integer ranges) even though the Python side validates first —
defence in depth, and the only thing stopping a compromised client. Install target:
`/var/lib/webosbrew/webos-foundry/dispatch.sh`. The authorized_keys entry
(`command="sh /var/lib/webosbrew/webos-foundry/dispatch.sh",no-port-forwarding,no-agent-forwarding,no-X11-forwarding,no-pty,restrict`)
is written once by `wof pair` (§6).

| Verb (dispatcher.py builder) | Grammar | Runs |
| --- | --- | --- |
| `status` | `status` | `sh .../status.sh` |
| `details` | `details` | `node .../details.js` |
| `remote` | `remote (wake\|power_off\|home\|back\|up\|down\|left\|right\|ok\|mute\|unmute\|volume_up\|volume_down)` or `remote hdmi [1-4]` | `node .../remote.js <action> [value]` |
| `settings-list` | `settings-list` | `node .../settings.js list` |
| `settings-set` | `settings-set [A-Za-z][A-Za-z0-9_]* [A-Za-z][A-Za-z0-9_]* [A-Za-z0-9+/]{1,4000}={0,2}` (category, key, base64 of `{value, context}`) | `node .../settings.js set <category> <key> <b64>` |
| `notify-toast` | `notify-toast [A-Za-z0-9+/]{1,400}={0,2}` | `node .../notify.js toast <b64>` |
| `notify-say` | `notify-say [A-Za-z0-9+/]{1,400}={0,2}( [0-9]{1,2})?` | `flock -w 10 -E 75 <lock> node .../notify.js say <b64> [volume]` |
| `notify-overlay` | `notify-overlay [A-Za-z0-9+/]{1,8000}={0,2}` | `node .../notify.js overlay <b64>` |
| `screenshot` | `screenshot [0-9]{2,4} [0-9]{2,4} (jpg\|png)` | capture one-shot, cat, rm (see `capture.py`) |
| `stream-start` | `stream-start [0-9]{2,4} [0-9]{2,4} [0-9]{1,3} [0-9]{1,4} [0-5]` (width height fps seconds dump) | `exec .../vtcap/vtcap -w .. -h .. -f .. -t .. -d ..` (binary frames go straight to the SSH channel's stdout; the command itself is `exec`'d so the process IS the SSH session, making SIGTERM on the client side the only way to stop it) |
| `process-image` | `process-image [A-Za-z][A-Za-z0-9_-]* [0-9]{2,4} [0-9]{2,4}` (profile, width, height; the MP4 payload is piped as stdin via the Transport's `data=` argument, not inline in the command) | `flock -n <lock> node .../process-image.js <profile> <width> <height>` (reads the video from stdin) |
| `process-audio` | `process-audio [A-Za-z][A-Za-z0-9_-]* [0-9]{1,2}` (profile, seconds; WAV payload via stdin) | `flock -n <lock> node .../process-audio.js <profile> <seconds>` |
| `idle-wait` | `idle-wait` | `flock -w 25 <lock> true` — blocks until no processing job holds the TV lock |
| `install` | `install (status.sh\|details.js\|notify.js\|settings.js\|remote.js\|process-image.js\|process-audio.js\|dispatch.sh) [A-Za-z0-9+/]+={0,2}` | writes the named file under `/var/lib/webosbrew/webos-foundry/`, `chmod 644` (`755` for `dispatch.sh`/`*.sh`), atomically (`.new` then `mv`) |
| `install-overlay` | `install-overlay [A-Za-z0-9+/]+={0,2}` | base64 of the packaged overlay IPK; installs via `luna-send .../appInstallService/dev/install` the same way `pairing.py`/`install.py` already proved on this project (see the existing `c5_overlay.py` for the exact IPK byte layout to reuse) |
| `uninstall-overlay` | `uninstall-overlay` | `luna-send .../appInstallService/dev/remove {"id":"dev.webosfoundry.overlay",...}` |
| `install-vtcap` | `install-vtcap [A-Za-z0-9+/]+={0,2}` | writes the native binary + registers the dev-mode role/manifest under `/var/luna-service2-dev/` exactly as the existing `c5_capture.install_role()` does, generified to `dev.webosfoundry.vtcap` naming, then `ls-control scan-volatile-dirs` |
| `uninstall-vtcap` | `uninstall-vtcap` | removes only the files `install-vtcap` created |
| `uninstall-all` | `uninstall-all` | removes every file under `/var/lib/webosbrew/webos-foundry/`, the overlay app, the vtcap role, and finally itself; does **not** remove the authorized_keys line (that is printed for the user to delete by hand, since dispatch.sh cannot edit the file sshd is currently reading its own forced-command from without a race) |

`LOCK` is `/tmp/webos-foundry.lock` (TV-side, tmpfs). `settings.js`/`remote.js`/`notify.js` are
direct ports of the already-proven logic in this session's `c5_tv.py` NODE block and
`tv-c5-notify.js` — same Luna calls, same readback/scope checks, same error strings — only the file
layout and app id change. `process-image.js`/`process-audio.js` port `tv-ai-image.js`/
`tv-ai-audio.js` unchanged in their Luna/ffmpeg logic.

**Consumers:** `dispatcher.py` (builds these strings), `tv.py`, `notify.py`, `capture.py`,
`process.py`, `install.py`, `pairing.py`; `tests/` assert the regexes with known-good/known-bad
strings without ever opening a socket.

## 4. Python module signatures

```python
# tv.py
def get_status(transport) -> dict          # {"power","raw_power_state","source","app_id","is_luma","temperature_c","temperature_source","volume","muted"}
def get_details(transport) -> dict         # {"lux","panel_hours","panel_temperature_c","pixel_refresher","power_on_reason","power_history","signal","sleep_timer","usage_today"} — each field may be None
def get_settings(transport) -> list[dict]  # [{"category","key","label","value","values","available","context"}]
def set_setting(transport, category, key, value, context) -> str
def remote(transport, action, value=None) -> str   # "wake" sends a UDP magic packet locally and does not touch transport
REMOTE_ACTIONS: tuple[str, ...]
SETTINGS: tuple[tuple[str, str, str], ...]          # (category, key, label) — the only settings ever read/written

# notify.py
def toast(transport, text: str) -> str
def say(transport, text: str, volume: int = 15) -> str
def overlay_show(transport, card: dict) -> str      # card schema identical to this session's tv-c5-notify.js `card()`
def overlay_hide(transport) -> str

# capture.py
def screenshot(transport, width=1920, height=1080, fmt="jpg") -> tuple[bytes, str]   # (data, content_type)
def stream(transport, width=160, height=90, fps=30, seconds=0, dump=2) -> Iterator[tuple[int, int, bytes]]

# process.py
IMAGE_PROFILES: tuple[str, ...]
AUDIO_PROFILES: tuple[str, ...]
def enhance_image(transport, input_path, output_path, profile=...) -> dict
def enhance_audio(transport, input_path, output_path, profile=...) -> dict

# pairing.py
def pair(host, root_key_path, *, port=22, config_dir=None) -> Config   # one-off root-key transport; writes dispatcher+key; never persists the root key

# install.py
INSTALL_FILES: tuple[str, ...]     # the plain-file verb's whitelist, must equal dispatch.sh's list
def install(transport, *, overlay=True, vtcap="auto") -> dict          # "auto" = install vtcap only if tv-assets/vtcap/vtcap exists locally (built)
def update(transport) -> dict      # re-push INSTALL_FILES only
def uninstall(transport) -> dict
def status(transport) -> dict      # what's currently installed, for `wof doctor`
```

Every public function takes `transport` as its first argument (dependency injection for tests) and
raises `webos_foundry.errors.ValidationError` (a `ValueError` subclass) for a bad argument *before*
touching the transport, and `TransportError`/`RuntimeError` for anything the TV itself rejected.
`cli.py` and `server.py` are the only two places that construct a real `SSHTransport` from the saved
`Config`.

## 5. HTTP API (`server.py`)

Same route catalogue shape already proven in this project's `c5_web.py` (`GET /api` returns the
full self-describing catalogue: method, path, group, summary, body, query, returns, tv, notes,
example — keep that shape verbatim, it is the part users and the HA integration rely on). Changes
for a multi-install, non-loopback-capable server:

- **Auth:** every route except `GET /api` (and the static UI files) requires
  `Authorization: Bearer <server_token>` when the server is bound to a non-loopback address; on
  `127.0.0.1`/`::1` the token is optional but still accepted (keeps `curl` on the TV host frictionless,
  while `wof serve --bind 0.0.0.0` for a separate HA host refuses to start without a token in the
  config or `--token`). A wrong/missing token on a non-loopback bind returns `401`.
- **CORS/Host checks**: identical DNS-rebinding and cross-site-write refusal already proven in
  `c5_web.py`'s `caller_error`, generalised to the configured bind host(s).
- Routes: `GET /api`, `GET /api/status`, `GET /api/details`, `POST /api/notify/toast`,
  `POST /api/notify/say`, `POST /api/overlay` (`{"hide": true}` or a card), `GET /api/screenshot`,
  `GET /api/screen/stream`, `POST /api/remote/{action}`, `GET /api/settings`,
  `PUT /api/settings/{category}/{key}`, `GET /api/jobs`, `POST /api/jobs`, `GET /api/jobs/{id}`,
  `POST /api/jobs/{id}/cancel`, `POST /api/jobs/{id}/release`, `GET /api/jobs/{id}/result` — same
  semantics as this project's existing `c5_web.py` (reserved-TV 409s, job lifecycle, upload sniffing).
  Add `GET /api/health` → `{"paired": bool, "tv_host": str|null}` with **no auth required at all**
  (HA's config_flow connection test and `wof doctor --remote` use it before a token is known to be
  valid, and it leaks only whether *some* TV is configured, never the token or host when unpaired).

**Consumers:** `web/app.js` (sends the token from `localStorage`, prompts once), the Home Assistant
integration's `api.py` (same bearer-token calls).

## 6. Pairing flow (what `wof pair` actually does)

1. User runs `wof pair --host 192.168.1.50 --root-key ~/.ssh/tv_root_key` (the key they already have
   from rooting; webOS Foundry never generates or needs this long-term).
2. A one-off `SSHTransport`-like object connects with that key, pins the host key into a fresh
   `known_hosts` file inside the config dir (`StrictHostKeyChecking=accept-new` **only for this one
   bootstrap connection**, never again).
3. Generates a new ed25519 keypair (`ssh-keygen -t ed25519 -N "" -f <config dir>/id_ed25519`, or the
   `cryptography`-free fallback described in `pairing.py` if `ssh-keygen` is unavailable: stdlib
   cannot generate SSH keys, so `ssh-keygen` is a hard requirement of `wof pair`, documented
   up front and checked by `wof doctor`).
4. Pushes `tv-assets/dispatch.sh` to `/var/lib/webosbrew/webos-foundry/dispatch.sh` (`mkdir -p`,
   `chmod 755`).
5. Appends one line to `/home/root/.ssh/authorized_keys` on the TV:
   `command="sh /var/lib/webosbrew/webos-foundry/dispatch.sh",no-port-forwarding,no-agent-forwarding,no-X11-forwarding,no-pty,restrict ssh-ed25519 AAAA... wof@<local hostname>`
   — appended, never overwriting the file; the user's existing unrestricted root key keeps working.
6. Saves `Config` (host, key_path, known_hosts_path; `mac`/`server_token` left for the user to add
   via `wof config set` or generated on first `wof serve`).
7. Immediately re-connects using the **new restricted key** and runs `wof install` so the TV is
   usable without ever needing the root key again this session.
8. The root-key transport object is discarded at the end of the function; `pairing.py` never writes
   the root key's path or contents to the config file or logs.

`wof pair` never contacts speakers or the HDMI output (it is pure file/SSH plumbing, so it is safe
to build and unit-test with `FakeTransport` right now).

## 7. Home Assistant integration contract

`homeassistant/custom_components/webos_foundry/` talks **only** to the `server.py` HTTP API over the
network (never SSH, never a key on disk inside HA). `config_flow.py` collects `host`, `port`
(default matches `server.py`'s default, e.g. 8765... pick and document one default), `token`; tests
the connection with `GET /api/health` then `GET /api/status` using the token. `__init__.py` sets up
a `DataUpdateCoordinator` polling `GET /api/status` every 15 s and `GET /api/details` every 60 s (two
coordinators, or one combined — document the choice in the integration's own README). Platforms:
`sensor` (power, source, temperature, volume, lux, panel hours/temperature, sleep timer, per-app
usage-today as attributes of one sensor), `binary_sensor` (is_luma, powered), `button` (wake),
`switch` or `media_player`-style mute/power if useful — document whichever is chosen. `notify`
platform or two `services.yaml` services (`webos_foundry.toast`, `webos_foundry.say`,
`webos_foundry.overlay_show`, `webos_foundry.overlay_hide`, `webos_foundry.remote`,
`webos_foundry.set_setting`) calling the matching POST/PUT routes. `manifest.json` declares
`"iot_class": "local_polling"`, no `requirements` beyond stdlib `aiohttp` (already a core HA dep).

## 8. What never changes without updating this file

The dispatcher grammar in §3, the config schema in §2, and the function signatures in §4 are the
seams every piece below builds against in parallel. If a builder needs a field this file does not
list, it adds the field here first (as an additive, backward-compatible change) rather than
inventing a private side channel.
