# HTTP API

`wof serve` hosts a JSON API and the static web UI (`/`, `/app.css`, `/app.js`) on one port
(default `8765`). The web UI and the Home Assistant integration are plain clients of this API.
`GET /api` returns the self-describing catalogue (method, path, group, summary, body, query,
returns, tv, notes, example for every route), so the live server is always the authoritative
reference; the tables below follow [ARCHITECTURE.md §5](../ARCHITECTURE.md).

In the examples, `TOKEN` is your server token and `host:8765` the address of `wof serve`.

## Authentication

* **Loopback bind** (`127.0.0.1` / `::1`, the default): the token is optional but still accepted.
* **Any other bind** (for example `--host 0.0.0.0` so a separate Home Assistant host can reach it):
  `wof serve` refuses to start without a token (from the config or `--token`), and every route
  except those below requires the header `Authorization: Bearer TOKEN`. A missing or wrong token
  answers `401`.
* **No token needed, ever:** `GET /api/health`, `GET /api` (the catalogue) and the static UI files.
  `GET /api/health` returns `{"paired": bool, "tv_host": str|null}`; it exposes the configured TV
  host only when paired, never the token.

```sh
curl -s http://host:8765/api/health
curl -s -H "Authorization: Bearer TOKEN" http://host:8765/api/status
```

Browser-origin checks apply as in the reference server: a `Host` header that is not one of the
server's configured hosts answers `421`, and cross-origin / cross-site non-GET requests answer
`403`. Plain `curl` and scripts are not affected.

## Conventions

* Every non-2xx response is `{"error": "message"}`.
* `400` bad argument (validated before the TV is contacted), `401` bad token, `404` unknown route
  or job, `405` wrong method, `409` the TV is reserved by a processing job or busy (for example a
  held `say` lock), `415` unsupported upload type, `502` the TV refused or did not answer
  (message is the TV's own error), `503` this install is not paired with a TV, `500` internal error.
  A `401` carries `WWW-Authenticate: Bearer`.
* JSON request bodies are limited to 64 KiB; uploads to 16 MiB.
* Read-only routes (`status`, `details`, `toast`) take no TV lock and keep working while a job runs.

## Route details

### `GET /api/status`

```json
{"power": "on", "raw_power_state": "Active", "source": "HDMI 1", "app_id": "com.webos.app.hdmi1",
 "is_luma": false, "temperature_c": 66.0, "temperature_source": "soc", "volume": 12, "muted": false}
```

`power` is `on|off|unknown`; `volume`/`muted` are `null` in standby; `temperature_c` is the SoC die
temperature (null when unreadable).

### `GET /api/details`

Same fields as [`wof details`](CLI.md#wof-details): `lux`, `panel_hours`, `panel_temperature_c`,
`pixel_refresher`, `power_on_reason`, `power_history`, `signal`, `sleep_timer`, `usage_today`; each
may be `null`.

### `POST /api/notify/toast`

Body `{"message": "1-200 characters, no control characters"}` → `{"message": "Toast shown on the TV"}`.

```sh
curl -s -X POST -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" \
  -d '{"message": "Dinner is ready"}' http://host:8765/api/notify/toast
```

### `POST /api/notify/say`

Body `{"message": "1-200 characters", "volume": 1-40}` (`volume` optional, default 15). Borrows Audio
Guidance, speaker volume and mute under the TV lock and restores them, so it answers `409` while a
processing job runs or the lock is held. The TV must be on.

```sh
curl -s -X POST -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" \
  -d '{"message": "Dinner is ready", "volume": 10}' http://host:8765/api/notify/say
```

### `POST /api/overlay`

Body is exactly `{"hide": true}`, or a card: a `root` widget tree, a multi-region card (`regions`), or
the shorthand fields compiled into an equivalent tree server-side:

```json
{"title": "Dinner", "body": "It is ready.", "lines": ["Table 4"], "image": "https://example.com/a.png",
 "kind": "success", "position": "top-right", "size": "m", "seconds": 10}
```

Shorthand fields are all optional but need at least one of `title`, `body`, `lines`, `image`: `title`
≤ 80 chars, `body` ≤ 400, `lines` ≤ 10 items of ≤ 120, `image` an `http(s)` URL ≤ 500 chars that the
**TV** can fetch, `kind` `info|success|warning|alert`. `position`
`top-left|top-right|bottom-left|bottom-right|center` (floating card, default `top-right`) or
`top|bottom|left|right` (a full-width edge bar or full-height edge panel), `size` `xs|s|m|l|xl|full`
(default `m`), `seconds` integer 0-300 (0 = until hidden, default 8) and `theme` apply to every form.
`theme` is `{"accent"?, "surface"?, "text"?, "muted"?, "line"?: "#rrggbb", "opacity"? 0.2-1, "radius"? 0-32,
"scale"? 0.75-1.5, "font"? sans|condensed|mono}`. A `root` tree replaces the shorthand entirely (the two are
mutually exclusive in one request): a node is `{"type": stack|row|text|image|badge|dot|progress|countdown|
clock|list|divider|compare|sparkline|section|event|stat|status|meta|grid|ticker|qr|svg, ...fields, "children"?: [...]}`.
`{"seconds"?, "theme"?, "regions": [{"position", "size"?, "root"}, ...]}` (1-4 regions with distinct
positions) draws several cards in the one overlay window — a top bar plus a side panel, say. Caps: depth
≤ 5, ≤ 80 widgets total across all regions/timeline frames, ≤ 49152 bytes of the final JSON. Full per-type field list:
[ARCHITECTURE.md §3a](../ARCHITECTURE.md). Unknown fields are refused. A TV in standby or an invalid card
answers `502` with the TV script's message. Response `{"message": "Overlay card shown"}` or `"... hidden"`.

Single cards and regions also accept `animation:{enter?,exit?,duration_ms?}` and floating `offset:{x?,y?}`.
`behavior:{on_foreground?:keep|hide|shrink,ambient_dim?:boolean}` opts into actual TV telemetry.
`{"timeline":[{"seconds":1..300,"card":<card>},...]}` plays up to four cards without nested timelines.
Omit outer `seconds` or use zero for the full sequence; a positive value is an overall deadline.
Repeated value updates retain unchanged renderer nodes and timers.

```sh
curl -s -X POST -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" \
  -d '{"hide": true}' http://host:8765/api/overlay
curl -s -X POST -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" -d '{
  "root": {"type": "stack", "gap": 12, "children": [
    {"type": "text", "text": "Dinner", "size": "l", "weight": "strong"},
    {"type": "progress", "value": 0.6, "label": "Cooking"}]}
}' http://host:8765/api/overlay
```

### `GET /api/overlay/schema` and `POST /api/overlay/validate`

Two helpers for people (and assistants) writing cards by hand. Neither touches the TV; both work
before pairing. `GET /api/overlay/schema` returns a JSON Schema (draft 2020-12) of the whole card body
(envelope, theme, regions, timelines, all 22 widgets with their enums and limits), generated from the server's
own validation constants, so it cannot drift from what `POST /api/overlay` accepts (`wof overlay
schema` prints the same). Hand it to ChatGPT, a JSON editor or a code generator.

`POST /api/overlay/validate` takes any candidate card and answers `{"ok": true, "card": <normalised
card>, "widgets": N, "bytes": N}` so you can see how close you are to the 80-widget / 49152-byte caps,
or `400 {"error": "..."}` with the exact reason — the same sentence `POST /api/overlay` would give,
naming the widget and field (`"Unknown text field: colour"`, `"stat left value must be ..."`). Unknown
widget fields are refused, never silently dropped, so a misspelt key is caught before it costs a
trip to the TV. The web UI's paste-JSON flow and `wof overlay check FILE` use this.

```sh
curl -s -H "Authorization: Bearer TOKEN" http://host:8765/api/overlay/schema > overlay-card.schema.json
curl -s -X POST -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" \
  -d @my-card.json http://host:8765/api/overlay/validate
```

### `GET /api/screenshot`

Query: `width` 64-3840, even (default 1920; height follows the 16:9 picture), `format` `jpg` (default)
or `png`. Returns the image bytes with `Cache-Control: no-store`. Copy-protected (HDCP) sources
answer `502`. **The image is whatever the connected device displays: private.**

```sh
curl -s -H "Authorization: Bearer TOKEN" "http://host:8765/api/screenshot?width=960&format=jpg" -o tv.jpg
```

### `GET /api/screen/stream`

Query: `width` `160` (default) or `320`, `height` `90` for width 160 (default) or `180` for 320, `fps`
10-60 (default 30). Returns `application/octet-stream`, close-delimited (no `Content-Length`): the
bytes `WOF1`, `u16le width`, `u16le height`, then frames of `width*height*3` bytes of RGB24, until the
client disconnects, a 10-minute cap passes or the server stops. One stream at a time (`409`
otherwise, and `409` while a job reserves the TV); `502` when the capture client cannot start (not
installed: `wof install --vtcap yes`). Reference measurement: 30.4 fps at 160×90 in the page. The
server keeps no frames.

### `POST /api/remote/{action}`

`action` is one of `wake`, `power_off`, `home`, `back`, `up`, `down`, `left`, `right`, `ok`, `mute`,
`unmute`, `volume`, `volume_up`, `volume_down`, `hdmi`. `hdmi` requires `{"value": 1-4}`;
`volume` requires an integer `{"value": 0-100}` and sets the TV speaker directly, with read-back.
Values above the TV's reported maximum are rejected, not clamped. Other actions take no value. Returns
`{"action": "...", "message": "what the TV confirmed"}`. `wake` is a LAN Wake-on-LAN broadcast from the
server host (needs `mac` in the config) and does not prove the TV woke; read `/api/status`. Answers `409` while a job holds the TV.

```sh
curl -s -X POST -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" \
  -d '{"value": 2}' http://host:8765/api/remote/hdmi
```

The Remote page caps its slider and + button at 40 until “Allow volume above 40” is checked.
That opt-in resets on page load; checking or unchecking it never changes the TV volume.
The API and CLI retain the full 0–100 range. Volume changes can unmute the TV; the confirmation reports the actual mute state.

### `GET /api/settings` and `PUT /api/settings/{category}/{key}`

`GET` returns a list of `{"category", "key", "label", "value", "values": [allowed now], "available",
"context": {axis: value}}` for the fixed set of AI picture/sound settings ([CLI.md](CLI.md#wof-settings)).
`PUT` body is `{"value": "<one of values>", "context": <the context object from GET>}`; the server
rechecks scope, availability and allowed values on the TV, writes, and reads back. A changed input or
picture mode since the read is refused. Returns `{"message": "..."}`.

```sh
curl -s -X PUT -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" \
  -d '{"value": "on", "context": {}}' http://host:8765/api/settings/sound/aiSound
```

### `GET /api/apps/bundled`

Lists the TV apps included with this project. The current entry is the overlay renderer:

```json
[{"id":"dev.webosfoundry.overlay","title":"Overglass Overlay","description":"Displays Overglass overlay cards on the TV.","version":"1.0.1","installed":true,"available":true}]
```

`installed` comes from the TV's installation status. `available` means this server can supply
the bundled package: project source on the PC, or the private staged IPK on the on-TV server.
Missing package files do not turn an existing installation into "not installed".

### `POST /api/apps/bundled/{id}`

Accepts no body or `{}`. Only `dev.webosfoundry.overlay` is accepted; URL, path, query, and
other installation options are rejected. This is separate from the third-party IPK installer.
The TV installer must complete and installation readback must succeed before the response is:

```json
{"id":"dev.webosfoundry.overlay","installed":true,"message":"Overlay renderer installed"}
```

Existing authentication and guest restrictions apply. Unknown IDs return `404`, invalid options
return `400`, and a TV reserved by processing or another change returns `409`. Unavailable source
or staged packages return `503`; installer/readback failures are errors, not successful installs.
The dispatcher holds the processing lock before writing the temporary IPK.

`wof install --tv-server` stages the renderer package outside the public web directory. Once
staged, the on-TV endpoint works without a PC. Re-run that command from an updated checkout to
refresh its package.

```sh
curl --fail -H "Authorization: Bearer $TOKEN" http://host:8765/api/apps/bundled
curl --fail -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{}' http://host:8765/api/apps/bundled/dev.webosfoundry.overlay
```

### Processing jobs

One processing job runs at a time and reserves the TV (remote/settings/say/overlay answer `409`).

* `POST /api/jobs?profile=ai-picture-sr&name=photo.png`: raw request body is the file
  (`Content-Type: application/octet-stream`); the kind (image PNG/JPEG or audio WAV) is detected
  from the content, `415` otherwise. Returns `202` and the job object. Profiles: image
  `ai-picture-sr` (default), `ai-picture`, `standard`; audio `ai-sound` (default), `clear-voice`,
  `standard`. Limits as in [`wof process`](CLI.md#wof-process).
* `GET /api/jobs` → `{"active": id|null, "jobs": [...]}` (no logs).
* `GET /api/jobs/{id}` → `{"id", "kind", "profile", "state", "outcome", "exit_code", "log", "result", "recovery_workspace", "release_error", ...}`;
  `state` is `running|cancelling|restoring|release_unconfirmed|done|failed|cancelled`.
* `POST /api/jobs/{id}/cancel` → `202`, the processor restores the TV before the job ends.
* `POST /api/jobs/{id}/release` → `202`; re-checks the TV lock after `release_unconfirmed`. The TV
  stays reserved until it succeeds.
* `GET /api/jobs/{id}/result` → image/png (3840×2160) or audio/wav (32-bit) as an attachment.

Uploads and results live in a private temporary directory deleted when the server stops; the last 20
finished jobs stay downloadable until then.

```sh
curl -s -X POST -H "Authorization: Bearer TOKEN" --data-binary @photo.png \
  "http://host:8765/api/jobs?profile=ai-picture-sr&name=photo.png"
curl -s -H "Authorization: Bearer TOKEN" http://host:8765/api/jobs/JOB_ID/result -o out.png
```

### Scenes

A scene is a named sequence of 1-20 steps (remote, setting, overlay, wait), run in order, stopping
at the first failure. Full step shapes and validation: [ARCHITECTURE.md](../ARCHITECTURE.md)
(search `## Scenes`).

* `GET /api/scenes` -> `{"scenes": {name: {"steps": [...]}}}`.
* `PUT /api/scenes/{name}` body `{"steps": [...]}` -> `{"message": "Scene saved"}`. An `overlay`
  step's card is validated and compiled into a widget tree here, not every time the scene runs.
* `DELETE /api/scenes/{name}` -> `{"message": "Scene deleted"}`; `400` if unknown.
* `POST /api/scenes/{name}/run` -> `{"messages": [one per completed step]}`; `404` unknown scene,
  `409` while a job reserves the TV, `502` at the step that failed (earlier steps already ran).

```sh
curl -s -X PUT -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" -d \
  '{"steps": [{"type": "overlay", "card": {"title": "Movie night", "seconds": 5}}]}' \
  http://host:8765/api/scenes/movie-night
curl -s -X POST -H "Authorization: Bearer TOKEN" http://host:8765/api/scenes/movie-night/run
```

### Local scheduler

Runs a saved scene automatically at a time of day. Needs `wof serve` (or the on-TV server) running
continuously; entries and detail: [ARCHITECTURE.md](../ARCHITECTURE.md) (search `## Local scheduler`).

* `GET /api/schedule` -> `{"entries": {id: {"scene", "time", "days", "enabled"}}}`.
* `POST /api/schedule` body `{"scene", "time": "HH:MM", "days"?: ["mon", ...], "enabled"?}` ->
  creates and returns `{"id", ...}`.
* `PUT /api/schedule/{id}` updates an existing id (`404` if unknown).
* `DELETE /api/schedule/{id}`.

```sh
curl -s -X POST -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" \
  -d '{"scene": "movie-night", "time": "20:00", "days": ["fri", "sat"]}' \
  http://host:8765/api/schedule
```

### Webhooks

A capability targets one saved scene or design. Management uses admin authentication; the capability
URL itself is sufficient to invoke its target. Keep it private and delete it to revoke access.

* `GET /api/webhooks` returns saved scene/design targets and labels.
* `POST /api/webhooks` accepts `{"scene":name,"label"?}` or `{"design":name,"label"?}`.
* `DELETE /api/webhooks/{token}` revokes it.
* `GET /webhook/{token}` describes the target and never executes it.
* `POST /webhook/{token}` executes. For a design, optional `{"values":{"score":"2 : 1"}}` fills
  existing `{{score}}` display placeholders or declared scalar binding targets.

Migration: replace GET triggers with POST. Unknown values or structural/URL changes are rejected.

```sh
curl -s -X POST -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" \
  -d '{"design":"match-day","label":"Score"}' http://host:8765/api/webhooks
curl -s -X POST -H "Content-Type: application/json" \
  -d '{"values":{"score":"2 : 1"}}' http://host:8765/webhook/TOKEN
```
